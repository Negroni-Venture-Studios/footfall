# Changelog

All notable changes to Footfall are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Footfall uses [semantic versioning](https://semver.org/).

## [Unreleased]

- `footfall test <folder>` runs the AI testers against a local folder. It copies only the files git would commit, so an ignored `.env` never reaches a container, and a folder outside git needs `--all-files`, which warns that it copies everything. It never reads or writes through a link, it never copies the repository's own git folder or a linked worktree's common folder, however a crafted index or a `.git` file names them, and it leaves out untracked files in any folder shaped like a git folder, such as a nested repository's. It refuses a submodule or a nested repository, whose files git does not list. With `--all-files` it leaves out every `.git`, every folder git names as a git folder, and every folder shaped like one, with a `HEAD` file and an `objects` folder, or a `commondir` file. git runs with none of Footfall's environment, no input and no way to fetch, and reads a repository someone else owns only where the system trusts it; the footfall image trusts `/repo`, where the dev stack mounts the repository under test. It asks the runner to prepare the app, start a copy for each persona and start the run's browsers, signs each persona in when the brief asks, then writes each persona's report, step trace and screenshots, a summary of the run and a table of the results. The run is stopped however it ends, and the throwaway password reaches only the seed step.
- `footfall runner` serves the runner, the one process that holds the Docker socket, on a Unix socket that only its own group can use.
- `footfall proxy` serves the egress proxy and its control socket.
- `FOOTFALL_DISK_BUDGET_MIB` sets how much disk the runner lets one run use, counting every copy of its app. It is 8192 MiB unless set, and a value that is not a positive whole number, an empty one included, stops the runner with an error.
- Each run's browser container puts a gate in front of Playwright's server, which listens on loopback alone. The gate passes on only a WebSocket upgrade for a path made fresh for that run, which only the orchestrator is told, and answers every other request with an empty 404, so code under test can neither learn the path nor launch a browser of its own there. Each connection has 10 seconds to send its request, and connections held open from one address cannot crowd out the orchestrator's. When the container stops, the gate stops run-server and everything it started within a few seconds, and if the gate goes, run-server goes with it.
- The browser image installs a Chromium managed policy that turns off Encrypted Client Hello, which the egress proxy refuses, and the run's Chromium starts as the full build, since the headless shell reads no policies.
- Every container the runner starts has an init process, and the browser container has 512 MiB of shared memory for Chromium.
- The host has no address on a run's network, so code under test cannot reach what the host serves, and every container the runner starts finds the egress proxy by name in its hosts file, since Docker's name service does not answer under gVisor.
- `deploy/dev/compose.yaml` runs the proxy, the runner and an orchestrator for development. Each is read-only, runs under an init process and has no capabilities beyond what it needs, only the runner mounts the Docker socket, and only the orchestrator receives the Anthropic key. The orchestrator mounts the repository under test read-only with its `.git`, and the footfall image carries git, so the copy is git's there too. With `FOOTFALL_RUNTIME=runc`, for a machine without gVisor, every command warns that containers start without it.
- The isolation workflow, `.github/workflows/isolation.yml`, builds the images, installs gVisor and starts the dev stack, then runs the sandbox's own tests in its orchestrator: what an app container can be, hold and reach, the egress proxy's decisions, the browser container's gate, and a whole `footfall test` run of the demo app. It records the peak memory of each kind of container in the job summary.
- Tiny Tasks, the demo app in `demo-app/`: a to-do list with twelve planted usability and accessibility bugs, listed in its `BUGS.md`, with a manifest and a brief for Footfall to test it.
