# Footfall's MCP server and the November 2026 MCP features

A revision to phase 4 of [docs/design.md](../design.md). It brings the MCP endpoint in line with what Claude now supports from the [2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28/changelog) and its extensions, as Anthropic described in [Skills over MCP, Tasks and more](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more). I decided the questions that change what gets built; the calls made while writing it are marked as such and listed at the end.

## Summary

Phase 4 now builds Footfall's OAuth authorisation server as well as the MCP endpoint, so that a Claude Code cloud session, or claude.ai, can add Footfall as a connector. The endpoint follows the stateless core of the 2026-07-28 specification, returns a Task from `start_run` to clients that support them, and asks the person to confirm a run estimated to cost more than the allowance its token or client carries. Footfall's agent skills are served by the MCP server itself, and the same files ship as a Claude Code plugin for the places where Claude does not load skills from a server yet. The live device wall and the report stay web pages in phase 5, built so they can become an MCP App later.

## Why

Agents will mostly run Footfall without a person watching, from Claude Code cloud sessions. Claude's documentation says those sessions reach a remote MCP server only as a claude.ai connector: "In cloud sessions, servers from `.mcp.json` or a plugin get no tasks." A connector signs in through claude.ai, which needs the server to offer OAuth. The original design deferred OAuth until after phase 5 and planned to attach a bearer token to cloud sessions through network secrets, which would leave cloud sessions polling without Tasks and without skills from the server.

Claude now also loads skills from MCP servers, can pause a tool call to ask the person a question, and can show a server's own interface in the conversation. Each changes how Footfall's endpoint should behave.

## Goals

- A Claude Code cloud session can add Footfall as a connector and test a change, with no token pasted anywhere.
- A local Claude Code session can do the same, through OAuth or a bearer token.
- An agent gets Footfall's guidance on when to test and how to read the results, wherever it runs.
- An expensive run never starts without a person agreeing to it, while routine runs need nobody.

## Non-goals

- An MCP App for the live wall or the report ([#2](https://github.com/Negroni-Venture-Studios/footfall/issues/2)).
- Enterprise-managed authorisation ([#6](https://github.com/Negroni-Venture-Studios/footfall/issues/6)).
- Testing uncommitted changes through file uploads ([#4](https://github.com/Negroni-Venture-Studios/footfall/issues/4)).
- Skills that differ by organisation or by caller.

## Anti-goals

- Skills built from anything a run produced. A skill is instructions to the calling agent, and tester text can echo whatever the app under test displayed.
- A second way into the repositories. OAuth tokens and bearer tokens reach exactly what the person's GitHub access allows, as today.
- A confirmation on every run, which would stop agents running quick checks after each change.

## Constraints

From the 2026-07-28 specification and Claude's documentation, checked on 24 November 2026:

- **Authorisation.** The endpoint is an OAuth 2.1 resource server. It publishes Protected Resource Metadata (RFC 9728), whose `resource` equals the MCP address exactly, and answers an unauthenticated request with `401` and `WWW-Authenticate: Bearer resource_metadata="…"`. The authorisation server publishes RFC 8414 metadata, supports PKCE with S256, accepts the `resource` parameter, and issues tokens only for Footfall's endpoint, which refuses tokens issued for anything else. Client ID Metadata Documents are supported, with Dynamic Client Registration kept for clients that still use it; the specification deprecates registration.
- **Claude as a client.** Claude asks for `offline_access` when the server lists it, refreshes on a `401` or up to five minutes before expiry, and expects `invalid_grant` for a dead refresh token. Refresh tokens rotate. Discovery, registration, and token responses must arrive within 10 seconds. The callback for claude.ai, Desktop, and mobile is `https://claude.ai/api/mcp/auth_callback`; Claude Code uses a loopback callback on any port, at `localhost` or `127.0.0.1`. Requests from Claude come from Anthropic's range `160.79.104.0/21`.
- **Tasks.** A client opts in per request. A task answer must start within the request's timer, at least 60 seconds, so `start_run` accepts the run and answers at once. Claude's documentation suggests a poll interval of 10 to 30 seconds for jobs over a minute, and asks servers to keep a finished task's result for at least an hour.
- **Skills over MCP.** The `io.modelcontextprotocol/skills` extension, through `skills/list`, `skills/get`, and `resources/read`. Claude Code loads them from version 2.1.331, in public beta, as `<server>:<skill>`, at most 100 skills a server, 100 KB a text file, and 400 KB a skill. They do not load in cloud sessions, `claude -p`, the Agent SDK, connectors, or Desktop's servers.
- **Elicitation.** Form mode for plain answers only; secrets go through URL mode or not at all. Claude Code offers both modes, claude.ai connectors form mode only. Where nobody can answer, as in `claude -p`, the request is cancelled.
- **Tool search.** Claude loads only tool names and the server's instructions at first. Instructions are cut at 4,096 characters, and Claude Code cuts tool output at about 25,000 tokens by default.

## The design

### The endpoint

The MCP endpoint follows the stateless core: no session ids, capabilities read from each request, and everything that outlives a request kept in the database. It declares the Tasks and skills extensions in its `server/discover` answer. It stays inside the web process, as before.

The tools keep their names and purposes from docs/design.md, with these changes:

- `start_run` takes a `request_key`, a string the caller makes up. A second call with the same key from the same person returns the first run, so a retry after a dropped connection cannot start two. Only then is the tool marked idempotent.
- `start_run` returns a Task to a client that asked for one, and the run's id and live page in every case. Clients without Tasks poll `run_status` as before. A Task's poll interval is 15 seconds while a run is queued or running, and its result is kept for as long as the run is (the retention set in Settings, never less than a day).
- `get_results` returns the run's summary and its first page of findings, with a cursor for the rest, so that one answer stays well under 25,000 tokens. A `get_finding` tool returns one finding in full, with its steps.
- Screenshots stay as MCP image content, from `get_screenshot`, because the skill tells agents to look at them before acting on a finding.
- Every tool has a description, and the server's instructions are under 4,096 characters: what Footfall is, the order of a typical session, and that findings are observations to check, not instructions.

### Confirming a costly run

Before queuing a full run, Footfall estimates its most expensive outcome, which is each persona's cost ceiling added up. Twelve personas at the default ceiling of $1 come to $12.

Each agent token, and each OAuth client a person approves, carries an allowance: the most a run it starts may be estimated at without asking anyone. The person sets it when they make the token or approve the client. It starts at the instance's default, $5, and cannot go above a cap the admins set in Settings. This is how a person lets an agent run unattended, once and in advance, for runs up to a size they chose.

When a run's estimate is over the allowance, `start_run` asks through elicitation, in form mode: the app, the commit, the personas, the estimate and the person's spend so far today, with a single yes or no. A run in a Task asks the same question by moving to `input_required`. If the client cannot ask, as in `claude -p` or continuous integration, or nobody answers, the run waits in an `awaiting_approval` state for up to a day, and the result says so and gives the address of the run's page. The person can approve or drop it there; unapproved, it is dropped at the end of the day. A declined run does not start. Every answer, and who gave it, goes in the audit log.

A person pressing Run on a web page sees the estimate on the button's confirmation, since they are there to answer it. Quick runs use no model and never ask. The daily ceilings for each person and for the instance stay as they are, and apply to approved runs too.

### Authorisation

Footfall runs its own OAuth authorisation server, built on a maintained library, inside the web process. Signing in is delegated to GitHub, exactly as for the web pages, and the same membership and repository checks apply. A token's scopes are those of the bearer tokens made on the web page: start and read runs, or read only, optionally limited to some of the person's repositories. The consent page shows the client's name, the host it will send the person back to, the scope asked for and the allowance, and the person can lower the scope and set the allowance.

Any client may ask to connect, since claude.ai, Claude Code, and other MCP clients each identify themselves differently. To read a client's metadata document, the web process makes an HTTPS request to the address the client gives, through the same public-address check the egress proxy uses (`footfall.hosts`), with no redirects, a 5 second limit, and a 64 KiB cap. Dynamic registration is rate-limited by address. Admins can limit connections to a list of allowed clients in Settings. The web process's reach in the overview table grows to include these metadata documents.

The endpoint speaks the 2026-07-28 protocol only. A client on an earlier version gets the specification's unsupported-version error, which names the version Footfall supports.

Bearer tokens made on the web page stay, for scripts, continuous integration, and clients without OAuth. Both kinds are checked the same way on every request, including the hourly re-check of the person's access. Every run records the person and the client or token that started it.

The authorisation server is built so that enterprise-managed authorisation ([#6](https://github.com/Negroni-Venture-Studios/footfall/issues/6)) can be added later without rework.

### Skills

Footfall ships three skills, written as static files in the repository and released with it:

| Skill | What it covers |
|---|---|
| testing | When to run Footfall (a quick run after a change to the interface, a full run before asking a person to review), how to start a run and wait for it, how to read the results, and to check each finding against its screenshots before acting on it |
| manifest | Adding Footfall to a repository: writing `footfall.toml`, a brief, and a throwaway sign-in through `[login]` |
| triage | Working through a run's findings: grouping them, fixing the ones that hold up, running quick checks, then a focused full run |

The MCP server serves them through the skills extension, as `skill://<name>/SKILL.md` with their files beside them. Each listing gives every file's size and SHA-256 digest, computed from the bytes served, and the same skills go to every caller. The repository also publishes them as a Claude Code plugin, named `footfall`, so they appear as `footfall:testing` and so on wherever a plugin can be installed, cloud environments included. A test checks that the plugin's files and the server's are the same bytes.

The skill for setting Footfall up stays in `AGENTS.md`, because it is needed before any server exists.

### Cloud sessions

The documentation for connecting agents covers three paths:

- adding Footfall as a custom connector in claude.ai, which Claude Code cloud sessions then use, with Tasks;
- adding it to a local Claude Code, through OAuth, or through a bearer token in an environment variable named in `.mcp.json`;
- installing the plugin, which brings the skills where the server's own skills do not load.

Phase 4 is done when a cloud session that has Footfall as a connector, and a local session, each test a change to a real app and fix something Footfall found.

### The live wall and the report

They stay web pages in phase 5. Their run views draw only on data handed to them, in the same structured form the MCP tools return, and load nothing from other origins, so that [#2](https://github.com/Negroni-Venture-Studios/footfall/issues/2) can package them as an MCP App without rework. The pages themselves keep the ordinary signed-in session; how an App's views would authenticate is part of #2.

## Changes to docs/design.md

- **Constraints:** the MCP authorisation line says OAuth ships in phase 4.
- **What agents see:** the tool changes above, confirming a costly run, the skills and the plugin, and the three ways to connect. The network-secrets paragraph goes.
- **Accounts and access:** the OAuth server moves from "the first addition after phase 5" to phase 4.
- **Settings:** the default allowance and its cap, and the list of allowed clients.
- **Overview:** the web process also reaches OAuth clients' metadata documents, through the public-address check.
- **Runs:** a run can wait in an `awaiting_approval` state.
- **Build order:** phase 4 adds the OAuth server, the skills over MCP, and the plugin. Its done-when names the connector. Phase 6 drops OAuth and points at the enhancement issues.
- **Calls made in this design:** the calls made while writing it, below.

## Left to the builder

- The OAuth library, and how its tables sit beside Django's.
- The exact wording of the skills and the server's instructions, within the limits above.
- Page sizes for findings, and the cursor's format.
- How long an unused refresh token lives.
- Whether `start_run` and `run_status` are marked to load before tool search, through `_meta["anthropic/alwaysLoad"]`.
