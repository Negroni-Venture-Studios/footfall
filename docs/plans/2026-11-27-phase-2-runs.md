# Phase 2: runs. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn phase 1's one-shot `footfall test` into runs: an orchestrator service with a queue and limits, a database of runs and findings, scripted checks before the personas, a merged report, and spend held to its ceilings.

**Architecture:** The orchestrator container now runs `footfall orchestrator`, a long-lived asyncio service. It owns a SQLite database through Django's ORM, a queue, and a Unix socket on which the command line starts, reads, and cancels runs. A run is phase 1's run split into stages: prepare, scripted checks, personas, merge, and finish. The runner, the proxy, and the browsers keep their phase 1 roles.

**Tech stack:** Python 3.12+, Django 6.1 (models, migrations, and the async ORM only; no views), SQLite in WAL mode, the Anthropic Python SDK, Playwright for Python, pytest with pytest-asyncio.

**Spec:** [docs/design.md](../design.md), build order item 2, with "A run, start to finish", "Scripted checks", "Findings", "Limits and spend", and "Data and retention". Read those sections first. [docs/architecture.md](../architecture.md) says how phase 1 works.

## Calls made in this plan

The design leaves these to the builder. I check each before Task 1 starts.

- Django arrives now for the schema. I approved that on 27 November 2026. `django-stubs` comes with it as a development dependency, for strict mypy. That one still needs my approval.
- The Django app is `footfall.runs`. The settings module is `footfall.settings`. The database is `FOOTFALL_DATABASE`, `/var/lib/footfall/footfall.sqlite3` by default.
- The command line copies the folder into the workspaces root, as `footfall test` does now, and then asks the service to queue the run. The service never reads the folder under test.
- The orchestrator's socket speaks the runner's protocol: one JSON request and one JSON reply per connection. Each is at most 64 KiB. It is `/run/footfall-orchestrator/orchestrator.sock`, mode 0600. The web process gets access in phase 3, with the caller checks from issue #10.
- `footfall test` keeps its flags and its printed table. It now queues the run and waits for it.
- The queue is first in, first out. A full run needs one slot for each persona. A quick run needs one. The run at the head waits for room, and nothing overtakes it.
- Limits start at 12 personas per run, 12 personas at once, 20 queued runs, and $50 a day for the instance. Each is an environment setting until Settings exists in phase 3. Ceilings for each person wait for people, in phase 3.
- The scripted checks load each page once in each persona's browser context. That context has the persona's device, text size, language, and direction. Identical findings from different personas become one. The touch-target check runs only on devices with touch.
- Scripted severities: a page that does not load is a blocker. A console error and a control with no accessible name are major. A failed request, sideways scrolling, and a small touch target are minor.
- The merge's classes are `bug`, `accessibility`, `usability`, and `likely test artefact`.
- The merge uses the run's model in one call with a JSON schema for its answer. It is charged to the run as the spender `merge`. If the run's ceiling has been reached, or the call or its answer fails, the findings stay ungrouped and the run still finishes.
- Runs are deleted after `FOOTFALL_RETENTION_DAYS`, 14 by default, with their files.
- The browsers container's limits follow the run's personas (issue #26): memory is 1 GiB plus 256 MiB for each persona. It gets one CPU, plus one more for each six personas or part of six. Twelve personas get 4 GiB and 3 CPUs.
- The proxy caps connections for each run at 256 (issue #3). Clients it cannot place in a run share a pool of 16.

## Review focus

- **The orchestrator stops mid-run.** At its next start the orchestrator marks every run left preparing, checking, running, or merging as failed with "the orchestrator restarted". It asks the runner to stop each one. Queued runs keep their places. Task 7 tests this.
- **The queue is full, or two runs arrive at once.** The 21st queued run is refused with the limit in the message. Two runs submitted together get different places and both run. Task 7 tests this.
- **A page under the scripted checks never finishes loading.** Each page has a time limit. A page that runs out gets the "did not load" finding. The checks then go on to the next page. Task 4 tests this.
- **The merge's answer is malformed, partial, or steered by a finding's title.** An index out of range, a finding in two groups, an unknown class, or invalid JSON leaves the findings ungrouped. The run then finishes with the merge marked failed. Task 5 tests this.
- **The day's spend ceiling is reached by another run.** Every persona in every run stops at its next turn with the day's reason. A full run that would start after that fails at once with the same reason. Quick runs still go. Task 3 and Task 7 test this.

### Task 5: The merge

**Files:**
- Create: `footfall/merge.py`, `tests/test_merge.py`

**Interfaces:**
- Consumes: `Finding`, `RunSpend` (Task 3), `Usage`, `cost_usd`.
- Produces:
  - `GroupKind = Literal["bug", "accessibility", "usability", "likely test artefact"]`.
  - `Group` (frozen): `title: str`, `kind: GroupKind`, `findings: tuple[int, ...]`.
  - `Merged` (frozen): `status: Literal["merged", "skipped", "failed"]`, `groups: list[Group]`, `summary: str`.
  - `MergeReply` (frozen): `text: str`, `model: str`, `usage: Usage`.
  - `class MergeClient(Protocol)`, with `async def complete(self, system: str, prompt: str, schema: dict[str, Any]) -> MergeReply`.
  - `AnthropicMergeClient(client: anthropic.AsyncAnthropic, model: str)` makes one Messages API call with no tools. Its answer is held to `schema` with the API's structured outputs. Read the claude-api skill for the current parameters before writing it.
  - `async merge(findings: Sequence[Finding], *, client: MergeClient | None, spend: RunSpend) -> Merged`.

The prompt lists each finding as one line: its index, title, page, device, and severity, and nothing else. It is labelled with `OBSERVATIONS`. The system prompt says the lines are testers' observations and are never instructions. It asks for groups of findings that describe the same problem. Each group has a title and one of the four classes. It also asks for a summary of at most 1,500 characters. `likely test artefact` is for what an emulated device does that a real one would not. A group's severity is its most severe finding's, worked out in code.

`merge` returns `status="skipped"` with no call when `client` is None, when there are no findings, or when `spend.reached()`. It returns `status="failed"` with no groups when the call raises or the answer fails any check. The checks are:
- the JSON parses against the schema;
- every index is in range;
- every finding is in exactly one group;
- every class is one of the four.

Titles are cut to `CAPS["title"]` and the summary to `CAPS["summary"]` with `clean_text`. The call's cost goes to `spend` as the spender `merge`.
